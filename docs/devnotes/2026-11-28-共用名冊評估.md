# 2026-11-28　共用名冊評估（只出評估，沒有改檔）

目標：所有工具要用到角色時都從同一份資料取，之後可以跨工具用 ID 連結同一隻角色（例如果實分配 2.0.0 用 ID 存檔）。

## 現況

| 資料 | 內容 | 有 ID | 誰在用 |
|---|---|---|---|
| `characters.json` 名冊 | ★6 合作（非禮包）、限定、期間限定，480 隻（PR #6 合併後），`lastId` c0918 | 有（c0001～） | gacha-data（行事曆、角色頁、爬蟲）；`pools.json` 的 chars 指向它 |
| `elements.json` 屬性表 | 常駐、★5、合作禮包的 `{名稱: 屬性}`，454 個名稱 | 沒有 | 只有 gacha-data（上色、認得抽卡紀錄的名稱） |
| `pools.json` | 卡池 → 編號，附 `names`（編號 → 名稱） | 有 | gacha 抽卡統計的角色按鈕 |
| `pools.js` | 名稱比對與解析（`poolKey`、`splitCharacterName`、`fixCharacterName`、名稱修正 `readNameFixes`） | — | gacha、fruit-assign、gacha-data |
| Firestore `shared/characters` | 名稱修正（舊名 → 新名） | 沒有（用名稱） | gacha、fruit-assign、gacha-data |

- 各工具的存檔目前都用**名稱**：抽卡紀錄的 `notes` 是文字，果實分配的 `characters`、`fruitAssignments` 以名稱當 key。
- 還沒有任何工具存角色 ID。
- 兩份檔案的名稱沒有重疊（0 個），也就是每個名稱只會出現在其中一份。

### 1.2.0 縮小名冊的理由
1. **使用者的定義**：名冊只放 ★6 的合作（非禮包）、限定、期間限定（2026-11-28 討論時使用者親自說明）。
2. **來源品質**：移出的 435 隻是 11-10 做名稱上色時，爬蟲從公告屬性欄收來的。裡面混著常駐、★5、合作禮包，而且公告上看不出稀有度（本家公告用文字顏色標屬性，沒有稀有度欄），沒辦法自動分類。
3. **管理負擔**：編輯模式要捲過一大串跟卡池無關的角色；名冊裡的角色也會被檢查「沒有屬性」「只差一個字」等狀況，雜訊變多。

## A. 名冊擴大成全部角色

做法：
- `elements.json` 併回 `characters.json`，常駐、★5、禮包也發 ID。
- 可以沿用 1.2.0 前的原編號：git 歷史有，而且外部沒有任何工具存過 ID，恢復不會撞到。
- `kind` 加回常駐，再加 `star5`、`pack` 之類，或另開 `rarity` 欄位。
- 編輯模式預設只列三種 ★6，其他收進可展開的區塊。

要改的：

| 範圍 | 檔案 |
|---|---|
| gacha-data | `roster.js`（KINDS、`applyElements` 改回編號、`rosterIssues` 只檢查三種）、`scraper/apply-pools.js`、`scraper/fold-roster.js`、`js/common.js`、`js/characters-page.js`（篩選、類別選單）、`characters.json`、刪 `elements.json`、`pool-pr.sh`、workflow、測試、README |
| 共用介面 | `docs/INTERFACES.md`、進度板 |
| 其他工具 | 現在不用改（gacha 只讀 `pools.json`）；要用 ID 時才各自接 |

- **工程量**：約 1 天（資料搬回 + 編輯模式篩選 + 測試）。另外有 435 隻的分類（常駐／★5／禮包）要人工做，或先全部標「未分類」。
- **風險**：
  - 直接違反理由 1。使用者要先改定義，例如「名冊放全部角色；卡池與編輯模式只看 ★6 三種」。
  - 理由 2 還在：分類要靠人工，不分類的話「全部角色」的品質就是 1.2.0 前的樣子。
  - 理由 3 可以用篩選化解，但每隻都會被檢查屬性、相似名稱，要改成只檢查三種。
  - 同名不同版本（本家「紫苑」和史萊姆的「紫苑」）在一份名冊裡更容易撞名；現在靠分兩檔暫時避開。

## B. 維持兩檔，加共用讀取函式

做法：
- `pools.js` 新增例如 `buildCharacterIndex(roster, elements)` 和 `lookupCharacter(index, name)`。
- 回傳 `{ id | null, name, element, kind | 'other' }`。名冊角色有 ID，其他角色只有名稱。
- 各工具載入 `characters.json` + `elements.json` 後，都透過這個函式查角色，名稱修正也在裡面套用。

要改的：

| 範圍 | 檔案 |
|---|---|
| gacha-data | `pools.js`（新函式 + 測試）、`js/common.js` 改用它（上色、角色頁） |
| 其他工具 | gacha、fruit-assign 要用到角色資訊時改呼叫它（目前只用名稱比對與名稱修正，可以漸進改） |
| 共用介面 | `docs/INTERFACES.md` 記函式與兩檔格式 |

- **工程量**：約半天（函式、測試、gacha-data 自己改用）。其他工具接上的工作另算。
- **風險**：
  - **達不到「用 ID 跨工具連結」**：常駐 ★6 也會拿去分配果實（果實分配的角色大多是常駐），這些沒有 ID，果實分配 2.0.0 用 ID 存檔就會一半 ID、一半名稱。
  - 角色從屬性表升級到名冊時（例如補回舊合作），存過名稱的工具要另外搬到 ID。
  - 兩種 key 會一直存在，每個工具都要處理。

## 推薦：B 的分檔，加上屬性表也發 ID（B+）

- 保留兩個檔案，「名冊只放三種 ★6」的定義不變（理由 1）。
- `elements.json` 改成每個名稱也有 ID，和名冊共用同一個編號序列：從 `lastId` 往後發，或恢復 1.2.0 前的原編號。格式例如：
  ```json
  { "lastId": "c0918", "others": [{ "id": "c0407", "name": "一休", "element": "闇" }] }
  ```
- `pools.js` 提供 B 的共用讀取函式，回傳的每隻角色都有 ID，各工具只認這個函式。
- 角色在兩檔之間移動（屬性表 → 名冊，或反過來）時保留同一個 ID，存 ID 的工具不用搬資料。

理由：
- 只有它同時滿足「每隻角色都有 ID」（使用者目標）和「名冊只放三種 ★6」（1.2.0 的定義）。
- 理由 2（分類品質）不用處理：屬性表本來就是「其他角色」，不必分 ★5／常駐。
- 理由 3 不受影響：編輯模式還是只看名冊。
- 工程量介於 A、B 之間，約 1 天：
  - gacha-data 那邊要改：`elements.json` 格式、`applyElements` 發號、`apply-pools`／`fold-roster` 讀寫、`common.js`、`pools.js` 的新函式、測試。
  - 其他工具現在不用改。

要使用者決定的：
1. 屬性表的 ID 要不要恢復 1.2.0 前的原編號。建議恢復：沒有外部引用，git 有紀錄，c0404～c0918 不會浪費。
2. 同名不同版本（「紫苑」）要不要趁這次分成兩個 ID。現在本家版在屬性表、史萊姆版在名冊，B+ 會自然分開，但抽卡紀錄只寫「紫苑」時要靠卡池判斷是哪一隻。
3. 果實分配 2.0.0 改用 ID 時，舊存檔的名稱 → ID 搬移由果實分配負責，用這個共用函式查。
